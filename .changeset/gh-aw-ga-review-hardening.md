Hardened the Squad GH-AW (GitHub Agentic Workflows) source contract against nine confirmed GA-review findings:

- **`squad-improvement-gate.mjs`**: closed a test-coverage gap for rejecting a content-only modification of an already-tracked executable (`100755`) Markdown improvement target (the production `ALLOWED_FILE_MODE` guard was already correct; added realistic Git-mode regression/mutation tests).
- **`squad_approval_relay` contract**: made the `squad.md` → `squad-improvement-worker.md`/gate producer/receiver contract for the approval relay payload unambiguous as a JSON string end-to-end, preserving the distinct `squad_approval_relay` input name (gh-aw overwrites `aw_context`). Added compiled assertion/mutation coverage.
- **`squad-review-guard.mjs`**: confirmed and regression-tested that unauthorized/malformed override markers are rejected by authorized-admin-human filtering *before* cardinality/record parsing, so a malformed authorized record still fails closed and an unauthorized marker can never be counted.
- **`squad-planning-ontology.md`**: normalized the result-line template from `Result: ✅ PASS` to the exact `RESULT: PASS` string required by downstream parsers.
- **`squad-install-verifier.mjs`**: confirmed `verifyInstalledBytes()` normalizes only the one documented injected `source:` ownership-binding line before hashing, and fails closed on any other tamper; existing mutation-test table already covers this.
- **Numeric identity canonicalization**: numeric issue/comment IDs arriving via `issue_comment` are canonicalized to safe-integer strings before comparison against `workflow_dispatch` string inputs, with invalid forms rejected; covered by direct and relayed regression/mutation tests.
- **`squad-command-router.md`**: blocked replay of bot-authored standalone `/squad` issue/comment text while preserving trusted `workflow_dispatch` continuation and documented bot command behavior, covering both `created` and `edited` events.
- **`can_approve_pull_request_reviews`**: proved from gh-aw source that this is a single combined toggle gating both `GITHUB_TOKEN` PR creation *and* PR-review approval — it cannot be split via job-level `permissions:`. Per least-privilege policy (no weakened independent-human review gate), flipped to `false` across all public/enlistment/setup copies and added a fallback-to-issue mechanism (with a manual compare-URL link) to `squad-bootstrap.md` for when the push succeeds but the PR cannot be opened.
- **Mutable installation channel**: eliminated resolution of a mutable `commits/dev` ref for GA installs; setup now requires an explicit, pre-validated 40-character `SQUAD_SHA`, synchronized across public/enlistment docs and skill mirrors, while exact-SHA fixture testing remains unaffected.

Also redesigned the `can_approve_pull_request_reviews: false` bootstrap-PR fallback (surfaced by hosted-agent auto-review as a dead end: a plain compare-URL issue could never satisfy the bot-authorship-gated review contract) into a trusted signed-provenance-record path: the bootstrap run stamps a machine-readable provenance line (repo/run/base branch/head branch/head SHA/compare URL) into the fallback issue, and `squad-review-guard.mjs` validates a human-opened Cast PR against that record end-to-end — including bootstrap-run success — before granting the same base-controlled roles as the bot-authored path, with forged/unrelated/malformed records still failing closed.

No stable release is published by this change. Real (non-mocked) `gh aw compile --strict` against the canonical `workflows/*.md` sources continues to produce exactly the two documented warnings (`pull_request_target` advisory on `squad-review.md`, bot-trigger advisory on `squad.md`).

### Follow-up: bootstrap-PR-fallback trust hardening (auto-review on commit `9b45d116`)

- **`squad-bootstrap-validator.mjs`** (`findExistingBootstrapPrFallbackIssue`): a fallback-issue dedupe/ambiguity check previously counted any open issue matching only the plain, unsigned marker substring — any repo participant able to open an issue could post a decoy to suppress the real fallback issue or manufacture an "ambiguous" error. Candidates are now filtered to bot-authored, correctly titled, valid-provenance issues *before* counting/matching. Added forgery-regression tests proving a decoy issue can neither suppress real fallback-issue creation nor manufacture ambiguity.
- **`squad-review-guard.mjs`** (`validateBootstrapPrFallbackAttribution`): the fallback trust path bound a provenance record's `run_id` only to a historical successful run on the same *base-branch name*, unlike the bot-authored path, which also requires `run.head_sha === pr.base.sha`. Added the equivalent binding so a fallback issue can no longer cite an unrelated historical run on the same branch.
- **`scripts/gh-aw-hosted-e2e.mjs`** (`selectBootstrapFallback`): the hosted E2E only matched a plain-text branch marker and a compare-URL substring, not the full signed provenance record production actually requires — a hosted run could report success for a fallback issue production would reject. Added an independently-written `parseBootstrapPrFallbackProvenance` (not imported from the module under test) and rewired `selectBootstrapFallback` to exact-match the full record against an independently-rebuilt expectation, removing the now-redundant plain-text substring check.
- **`squad-command-router.md`**: added direct test coverage (populating `user.type`/`payload.sender.type`, previously never exercised by any fixture) proving the existing bot-authorship block is reachable and enforced for both `created` and `edited` events, with mutation-kill tests for both the author-type and sender-type halves of the check.

Also updated `docs/src/content/docs/guide/gh-aw.md`, `.github/agents.md`, `README.md` (removed a stale, contradictory `@dev`-tracking note left over from before the explicit-`SQUAD_SHA` policy), and all five synchronized copies of `skills/gh-aw-enlistment/SKILL.md` to describe the fallback-issue-first Cast PR flow instead of an unconditionally automatic one.

A second hosted-review pass on this same commit flagged two remaining stale passages the first doc pass missed: the `skills/gh-aw-enlistment/SKILL.md` anti-pattern list still said "automatic Cast PR" unconditionally, and the `docs/src/content/docs/guide/gh-aw.md` activation-canary/automatic-bootstrap checklist rows still described only the unconditional-automatic case (including when the linked research-proposals issue is created). Both are now corrected to cover the manual-fallback path and its provenance requirement.


### Follow-up: fresh Copilot review on commit `3bf5c01f` (7 findings)

- **Medium — edited-fallback-issue dedupe bug** (`squad-bootstrap-validator.mjs`, `findExistingBootstrapPrFallbackIssue`): dedupe matching accepted a fallback issue whose body had been edited after creation, even though `validateBootstrapPrFallbackAttribution` would reject that same edited issue at review time — a human editing the bot-authored issue (even to fix a typo) silently stalled the manual-recovery path with no new usable issue ever created. Candidates are now also required to have `created_at`/`updated_at` present and equal, mirroring the reviewer's unedited-issue requirement exactly. Added regression coverage for the edited-issue case and the missing-timestamp case.
- **E2E selector lifecycle gap** (`scripts/gh-aw-hosted-e2e.mjs`, `selectBootstrapFallback`): the hosted E2E's independent selector didn't mirror the open-state or unedited-timestamp checks the production validator enforces, so a hosted run could report success against a closed or edited fallback issue that production would reject. Added the same `state === 'open'` and unedited-timestamp checks, plus regression tests for both rejections.
- **Authorization accepted non-Bot, non-User account types** (`squad-review-guard.mjs`, `validateBootstrapPrFallbackAttribution`): the fallback-path PR-author check only excluded accounts literally typed `Bot`, so an `Organization`- or `Mannequin`-typed account (neither a human `User` nor an auditable `Bot`) could pass authorship. Tightened to require `pr.user?.type === 'User'`. The adjacent dispatch-router condition (which only decides *which* validator function to call, not whether it passes) was deliberately left unchanged, since the actual enforcement now lives entirely inside the called function and changing the router risks misrouting legitimately bot-authored ordinary PRs to the wrong validator. Added a regression test using an `Organization`-typed author.
- **Uncached collaborator-permission lookups** (`squad-review-guard.mjs`, `assertClearingReview`): the override-authorization loop issued one `collaborators/{login}/permission` API call per tagged comment, so a thread with many comments from the same admin (including decoys with a non-matching `head_sha`) multiplied API calls with no behavioral benefit. Added a per-login cache for the duration of a single evaluation. Added a regression test asserting exactly one permission call for two same-login comments.
- **Missing numeric-normalization/malformed-input test coverage** (`squad-improvement-gate.mjs`, `sameNumericId`): the top-level `SQUAD_IMPROVE_ISSUE_NUMBER`/`SQUAD_IMPROVE_APPROVAL_COMMENT_ID` env-string inputs already had malformed-input coverage, but the nested JSON-context fields (`origin.item_number`/`relay.item_number`) that also flow through `sameNumericId` did not. Production (`NUMERIC_ID = /^[1-9][0-9]*$/` plus a safe-integer bound) was already correct; this was a test-only gap. Added native-number cross-type-normalization proofs and `it.each` malformed/overflow-rejection tables for both the direct and relay-forwarded paths.
- **Missing exact-`RESULT:`-template test coverage** (`squad-planning-ontology.md`): production's "### 3.6 Validation Result" section already documents the exact `RESULT: <PASS | FAIL>` marker required by downstream parsers (no stale `Result: ✅ PASS` text remained); this was a test-only gap. Added a regression test pinning the exact template text and rejecting the stale form.
- **Fallback workflow lacked guidance after opening the compare PR** (`squad-bootstrap-validator.mjs`, `buildBootstrapPrFallbackIssueBody`): no GitHub event re-triggers `squad-bootstrap` the moment a human opens the fallback compare-URL PR — the next automatic run only fires on a push to squad-related paths on the default branch (i.e. at merge time) — so the linked research-proposals issue did not exist until merge. **Classification**: adding an automatic `pull_request`/`pull_request_target` trigger was considered and proven unacceptable by actual gh-aw/GitHub semantics — `gh aw compile --strict` hard-fails a `pull_request_target` trigger without an explicit safe-checkout override, and even with `checkout: false` (the same pattern already used by `squad-review.md`) it adds a second occurrence of the `pull_request_target` advisory warning, which would break the documented "exactly two compile warnings" contract. A manual `workflow_dispatch` re-run while the PR is still open is already fully sufficient by design (`classifyBootstrapState` recognizes an open, unmerged, matching PR and proceeds straight to `create_issue` — no merge required), so the actual gap was a missing instruction, not a missing trigger. The bot-authored fallback issue body now explicitly tells the human to manually re-run the workflow if they want the research issue before merging, and `skills/gh-aw-enlistment/SKILL.md` (canonical + 4 synced copies) now documents the same timing precisely. Added a regression test pinning the new instruction text and its position in the issue body; confirmed via a scratch `gh aw compile --strict` run that no new trigger or warning was introduced.

### Follow-up: fresh Copilot review on commit `1a9c4081` (3 findings, bootstrap-fallback dedupe/attribution)

- **Stale fallback-issue silently reused after the default branch advanced** (`squad-bootstrap-validator.mjs`, `findExistingBootstrapPrFallbackIssue`): the provenance record bound a fallback issue to a `run_id`/`head_sha` pair but never to the *base* commit the run executed against, so once the default branch moved forward, an old fallback issue (and its now-outdated compare link) kept matching and being reused forever instead of a fresh, correctly-based issue being filed. **Fix**: added a `base_sha` field to the provenance schema, populated from `context.sha` at the `squad-bootstrap.md` call site. **Proof this needs no new API call**: `squad-bootstrap.md` only reaches this code path behind its own top-level `if: github.ref_name == github.event.repository.default_branch` gate, so `context.sha` is guaranteed to already equal the default branch's exact current commit for every valid invocation — no extra lookup is required. Stale records (an open, correctly-titled, otherwise-valid issue whose embedded `base_sha` no longer matches) are now excluded from dedupe matching, causing a fresh issue to be filed rather than reusing a stale one. **Deliberate non-bump of `schema`**: the provenance `schema` version field is intentionally left at `1` despite this breaking field addition, because an old-format record (missing `base_sha`) now fails `parseBootstrapPrFallbackProvenance` entirely and is treated as unmatched — a safe fail-closed outcome (a fresh issue gets created) rather than a silent compatibility shim. Added regression coverage in `scripts/gh-aw-hosted-e2e.mjs` (`selectBootstrapFallback`'s independently-rebuilt expectation) and `test/gh-aw-bootstrap-workflow.test.ts`'s `findExistingBootstrapPrFallbackIssue` unit tests: a stale-`base_sha` issue returns unmatched (not ambiguous), and malformed/missing `expectedProvenance` arguments throw rather than silently matching anything.
- **Fallback review path never validated the Cast PR title** (`squad-review-guard.mjs`, `validateBootstrapPrFallbackAttribution`): the bot-authored (non-fallback) review path has always required the PR title to be the canonical `[squad] Cast your Squad`, but the human-opened fallback path never checked the title at all — any PR body carrying a forged-but-otherwise-valid provenance record would be granted the same trust regardless of title. Added the equivalent canonical-title check to the fallback path, closing the asymmetry. This also exposed a latent test-fixture bug: `test/gh-aw-review-guard.test.ts`'s `makeBootstrapPrFallback` happy-path default had been using a non-canonical placeholder title (`'Manually opened Cast PR'`) that only ever "worked" because production didn't check it yet — fixed to the canonical title (which the compare-URL link pre-fills in practice), with a new dedicated test asserting a non-canonical title is rejected even when a matching fallback issue exists.
- **Success notification assumed both a Cast PR and a research issue always exist** (`squad-bootstrap.md`): the run-success message was worded to always reference both, but the fallback path (PR-creation denied) only ever produces the fallback issue — no Cast PR exists until a human opens one. Reworded the message to be conditionally accurate for both the ordinary and fallback outcomes.

Also updated `docs/src/content/docs/guide/gh-aw.md` (~bootstrap-fallback provenance section) to document the new `base_sha` binding, the canonical-title requirement on the fallback path, and the staleness-exclusion/fresh-issue-refiling behavior. Regenerated `workflows/package/squad-bootstrap.md` and `workflows/squad-workflows.manifest.json` via `npm run gh-aw:integrity:write` to keep the installed mirror and embedded digests in sync with the source edits.
